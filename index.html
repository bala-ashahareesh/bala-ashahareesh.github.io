Kernel Optimisation for NPU

Mapping Math to Intuition

Rediscovering SoftMax as a Kernel Function

When building intuition for understanding Attention mechanism, I like to start from the concept of considering the memory state as an outer product accumulate process where the keys act as an index that decides how the values being updated can be distributed among the columns.

Ideally, when we think of "memory" as accumulated context or piece of information that is encoded in our d dimensional space as a vector, then it makes sense to think of it as a library that holds this info. To have no interference whatsoever, we would have the keys acting as an index that points to the location of the info (which we would call value). Since the keys are encoded as one-hot encoding, the position of the 1 is the position of the required value in the memory. Then the query would just be just be mathing that position.

\[ \text{Match}(q_i, k_j) = q_i^T k_j = \delta_{ij} = \begin{cases} 1 & \text{if } i = j \\ 0 & \text{if } i \neq j \end{cases} \]
Example: One-Hot Keys (The Library)

Suppose our memory has 3 slots. The keys are just the standard basis vectors (one-hot encodings):

\(k_1 = [1, 0, 0]^T\), \(k_2 = [0, 1, 0]^T\), \(k_3 = [0, 0, 1]^T\)

If we want to retrieve the value at the second slot, our query is simply \(q = [0, 1, 0]^T\). Taking the dot product with the keys gives us:

\(q^T k_1 = 0\), \(q^T k_2 = 1\), \(q^T k_3 = 0\).

This perfectly selects the second value with a weight of 1, and zeroes out the rest.

As easy and intuitive as it sounds, the "library" analogy comes with the same limitation mathematically. If every book needs a new slot, every piece of info or value would also need a new slot. Imagine every piece of context updating the column count by 1. Therein lies the need for superposition. This allows us to take advantage of the d dimensional space more.

Superposition

As hinted above, now is a good time to put the library analogy to rest. To think of your books as being distributed across different slots such that each slot corresponds to different parts of different books is probably where I would draw the line and say it is a futile exercise to carry the analogy further. Although while typing this out, we could in fact push this further if we rephrase the analogy from referring to single books and towards topics. Now a "slot" or value can be a genre or theme, so that a book can be distributed among them. When we have a key that tells us which book we want, it can be seen as a weighted sum of different values or genres.

Mathematically, if we have a value vector \(v \in \mathbb{R}^m\) and a distributed key vector \(k \in \mathbb{R}^n\), the memory update is an outer product \(v k^T\) (an \(m \times n\) matrix) accumulated into the memory state \(M\):

\[ M = \sum_{i=1}^{t} v_i k_i^T \]
Example: Outer Product Accumulation (Genres)

Let's map this to our new analogy. Our memory state \(M\) will hold the "genre profile" of our library. Let our values (\(v\)) represent the genres [Sci-Fi, Romance].

Book 1 is 80% Sci-Fi and 20% Romance: \(v_1 = \begin{bmatrix} 0.8 \\ 0.2 \end{bmatrix}\).
Its key (how it indexes into our memory slots) is: \(k_1 = \begin{bmatrix} 1 \\ 4 \end{bmatrix}\).

The outer product \(v_1 k_1^T\) distributes this book's genre profile across the columns according to its key weights:

\[ M_1 = v_1 k_1^T = \begin{bmatrix} 0.8 \\ 0.2 \end{bmatrix} \begin{bmatrix} 1 & 4 \end{bmatrix} = \begin{bmatrix} 0.8 & 3.2 \\ 0.2 & 0.8 \end{bmatrix} \]

Book 2 is 10% Sci-Fi and 90% Romance: \(v_2 = \begin{bmatrix} 0.1 \\ 0.9 \end{bmatrix}\).
Its key is: \(k_2 = \begin{bmatrix} 2 \\ 0 \end{bmatrix}\).

The memory state accumulates both books (superposition of their genres):

\[ M = M_1 + v_2 k_2^T = \begin{bmatrix} 0.8 & 3.2 \\ 0.2 & 0.8 \end{bmatrix} + \begin{bmatrix} 0.2 & 0 \\ 1.8 & 0 \end{bmatrix} = \begin{bmatrix} 1.0 & 3.2 \\ 2.0 & 0.8 \end{bmatrix} \]

Any query then matches with the key via inner product to give a score that decides how desired a particular value is.

Example: Query-Key Inner Product (Retrieval)

Let's say we are looking for a book with a query vector \(q = \begin{bmatrix} 1 \\ 0.5 \end{bmatrix}\). We calculate the score by taking the inner product with the keys of our stored books.

Score for Book 1 (\(k_1\)): \(q^T k_1 = (1 \times 1) + (0.5 \times 4) = 3.0\)

Score for Book 2 (\(k_2\)): \(q^T k_2 = (1 \times 2) + (0.5 \times 0) = 2.0\)

Because the score with \(k_1\) is higher, the query "desires" Book 1 (\(v_1\)) more than Book 2 (\(v_2\)). However, because we are using superposition, retrieving \(M q\) gives us a weighted sum of both genre profiles: \((3.0 \times v_1) + (2.0 \times v_2)\).

This gives us a beautiful associativity in the memory update.

If we retrieve from our memory state \(M\) using query \(q\), we get \(M q = \sum v_i (k_i^T q) = \sum v_i \cdot \text{score}_i\). Ideally, we want our scoring mechanism to behave as a selector: the desired value should have a weight of \(1\), and all undesired values should have a weight of \(0\) (a one-hot vector).

Unfortunately, the ensuing issue here is that even if the score is high for the desired value, the sum of undesired scores can still make the result noisy. This can be seen if we view it as an affine equation.

The Affine Noise Problem

If the desired signal is \(x\), and our desired weight is \(m\), the ideal output is \(y = mx\). However, the sum of undesired scores introduces a constant bias \(c\). Thus, the actual output is an affine equation: \(y = mx + c\).
