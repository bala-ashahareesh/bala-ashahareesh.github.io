Kernel Optimisation for NPU

Mapping Math to Intuition

In High school, my rebellious teenage phase forced me to believe that generalised conventions and equations were archaic forms of understanding math as they were devoid of any intuition. To me, if anything had to make sense, it needed to be intuitive. But I have grown to realise that despite being a great launcher for building motivation and appreciation for something, it should not be a self made ceiling wherein it prevents you from seeing how this form generalises over multiple domains.

And I guess fundamentally, that is what I will try to achieve through this blog. We will use intuition to formulate a theory and then feed it back to the equation itself, and then see how our intuition was a special case or implementation of a more general natural phenomenon.

Rediscovering SoftMax as a Kernel Function

When building intuition for understanding Attention mechanism, I like to start from the concept of considering the memory state as an outer product accumulate process where the keys act as an index that decides how the values being updated can be distributed among the columns.

Ideally, when we think of "memory" as accumulated context or piece of information that is encoded in our d dimensional space as a vector, then it makes sense to think of it as a library that holds this info. To have no interference whatsoever, we would have the keys acting as an index that points to the location of the info (which we would call value). Since the keys are encoded as one-hot encoding, the position of the 1 is the position of the required value in the memory. Then the query would just be just be mathing that position.

\[ \text{Match}(q_i, k_j) = q_i^T k_j = \delta_{ij} = \begin{cases} 1 & \text{if } i = j \\ 0 & \text{if } i \neq j \end{cases} \]
Example: One-Hot Keys (The Library)

Suppose our memory has 3 slots. The keys are just the standard basis vectors (one-hot encodings):

\(k_1 = [1, 0, 0]^T\), \(k_2 = [0, 1, 0]^T\), \(k_3 = [0, 0, 1]^T\)

If we want to retrieve the value at the second slot, our query is simply \(q = [0, 1, 0]^T\). Taking the dot product with the keys gives us:

\(q^T k_1 = 0\), \(q^T k_2 = 1\), \(q^T k_3 = 0\).

This perfectly selects the second value with a weight of 1, and zeroes out the rest.

Animation: one-hot keys — fill the slots, then query

As easy and intuitive as it sounds, the "library" analogy comes with the same limitation mathematically. If every book needs a new slot, every piece of info or value would also need a new slot. Imagine every piece of context updating the column count by 1. Therein lies the need for superposition. This allows us to take advantage of the d dimensional space more.

Superposition

As hinted above, now is a good time to put the library analogy to rest. To think of your books as being distributed across different slots such that each slot corresponds to different parts of different books is probably where I would draw the line and say it is a futile exercise to carry the analogy further. Although while typing this out, we could in fact push this further if we rephrase the analogy from referring to single books and towards topics. Now a "slot" or value can be a genre or theme, so that a book can be distributed among them. When we have a key that tells us which book we want, it can be seen as a weighted sum of different values or genres.

In this analogy: the Value (\(v\)) is the genre profile (e.g., how much Sci-Fi vs. Romance). The Key (\(k\)) is the thematic fingerprint or index (e.g., a mix of "Space" and "Castle"). The Memory (\(M\)) is the accumulated library.

Mathematically, if we have a value vector \(v \in \mathbb{R}^m\) and a distributed key vector \(k \in \mathbb{R}^n\), the memory update is an outer product \(v k^T\) (an \(m \times n\) matrix) accumulated into the memory state \(M\):

\[ M = \sum_{i=1}^{t} v_i k_i^T \]
Example A: Ideal Superposition (Orthogonal Keys)

Let's look at the ideal scenario where superposition works perfectly. Our values represent genres [Sci-Fi, Romance].

Book 1 is pure Sci-Fi: \(v_1 = \begin{bmatrix} 1 \\ 0 \end{bmatrix}\). Its thematic key is a mix of Space and Aliens: \(k_1 = \begin{bmatrix} 1 \\ 0.1 \end{bmatrix}\).
Book 2 is pure Romance: \(v_2 = \begin{bmatrix} 0 \\ 1 \end{bmatrix}\). Its key is a mix of Castle and Drama: \(k_2 = \begin{bmatrix} -0.1 \\ 1 \end{bmatrix}\).

Notice that the keys are distributed (not one-hot), but they are perfectly orthogonal (\(k_1^T k_2 = -0.1 + 0.1 = 0\)). The memory state accumulates as:

\[ M = v_1 k_1^T + v_2 k_2^T = \begin{bmatrix} 1 & 0.1 \\ 0 & 0 \end{bmatrix} + \begin{bmatrix} 0 & 0 \\ -0.1 & 1 \end{bmatrix} = \begin{bmatrix} 1 & 0.1 \\ -0.1 & 1 \end{bmatrix} \]

If we query with \(q = \begin{bmatrix} 1 \\ 0.1 \end{bmatrix}\) (looking for Book 1), we get:

\[ M q = \begin{bmatrix} 1 & 0.1 \\ -0.1 & 1 \end{bmatrix} \begin{bmatrix} 1 \\ 0.1 \end{bmatrix} = \begin{bmatrix} 1.01 \\ 0 \end{bmatrix} = 1.01 v_1 + 0 v_2 \]

We retrieve perfectly clean Sci-Fi, with absolutely zero noise from Book 2. Superposition is powerful if we can keep the keys orthogonal.

Animation: superposition — a key spreads its value over the columns

This gives us a beautiful associativity in the memory update.

If we retrieve from our memory state \(M\) using query \(q\), we get \(M q = \sum v_i (k_i^T q) = \sum v_i \cdot \text{score}_i\). Ideally, we want our scoring mechanism to behave as a selector: the desired value should have a weight of \(1\), and all undesired values should have a weight of \(0\) (a one-hot vector).

Where the Dot Product Falls Short

Look closely at what retrieval is actually doing. Every stored item gets a score from the query, and the output is a score-weighted sum of all the values: \(M q = \sum_i \kappa(q, k_i)\, v_i\). Here \(\kappa(q,k) = q^T k\), so the dot product is playing the role of a kernel: a similarity function that decides how much each memory is allowed to speak. Everything depends on how well that kernel behaves as a selector, and this is where the cracks start to show.

Unfortunately, the ensuing issue here is that even if the score is high for the desired value, the sum of undesired scores can still make the result noisy. This can be seen if we view it as an affine equation.

Example B: The Reality (Crosstalk & Noise)

In reality, thematic fingerprints overlap heavily. We cannot always keep the keys orthogonal. Let's use overlapping keys:

Book 1 (Mostly Sci-Fi): \(v_1 = \begin{bmatrix} 0.8 \\ 0.2 \end{bmatrix}\). Key (Space + Aliens): \(k_1 = \begin{bmatrix} 1 \\ 0.5 \end{bmatrix}\).
Book 2 (Mostly Romance): \(v_2 = \begin{bmatrix} 0.1 \\ 0.9 \end{bmatrix}\). Key (Space + Romance): \(k_2 = \begin{bmatrix} 0.5 \\ 1 \end{bmatrix}\).

The memory state \(M\) becomes a messy superposition of both.

Any query then matches with the key via inner product to give a score that decides how desired a particular value is. Let's query with \(q = \begin{bmatrix} 1 \\ 0.5 \end{bmatrix}\) (looking for Book 1):

Score for Book 1 (\(k_1\)): \(q^T k_1 = (1 \times 1) + (0.5 \times 0.5) = 1.25\)

Score for Book 2 (\(k_2\)): \(q^T k_2 = (1 \times 0.5) + (0.5 \times 1) = 1.0\)

Book 1 does win the contest, 1.25 vs 1.0. But the scores are so close that Book 2 still gets almost the same say. When we retrieve \(M q = 1.25 v_1 + 1.0 v_2 = \begin{bmatrix} 1.10 \\ 1.15 \end{bmatrix}\), the answer reads as slightly more Romance than Sci-Fi: the retrieval has been taken over by the book we did not ask for.

Animation: crosstalk — the highest score still loses the vote

That is the core limitation of the plain dot product as a kernel, and it comes in three flavours:

  • It does not sharpen. Similar keys get similar scores (1.25 vs 1.0), so the winner does not take all. We wanted a selector, but we got a gentle weighting.
  • Losers still contribute, and they add up. Every undesired item leaves a small non-zero weight. Individually harmless, but summed over many items (or one heavily overlapping item) they can outweigh the desired value.
  • The scores are unbounded and unnormalised. They can be large, small, or even negative, so they are not a clean set of weights that add to 1.

A better kernel would need to widen the gap between the winner and the rest, and turn the scores into proper weights. Hold on to that thought.

The Affine Noise Problem

If the desired signal is \(x\), and our desired weight is \(m\), the ideal output is \(y = mx\). However, the sum of undesired scores introduces a constant bias \(c\). Thus, the actual output is an affine equation: \(y = mx + c\).
